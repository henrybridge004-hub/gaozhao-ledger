# 钉钉表格结构与权限

## 推荐结构：三张表，不要把所有东西塞进一张表

| 表 | 内容 | 谁可见 | 是否公开 |
|---|---|---|---|
| `个人台账-<HR姓名>` | 标准候选人明细 | 本人、HRD、招聘运营 | 否 |
| `面试反馈明细-<HR姓名>` | 一场面试一行，含面评 | 本人、HRD、招聘运营 | 否 |
| `高招招聘漏斗` | 只放人数/场次/转化率/点数/排名 | 全组可读 | 是 |

如果钉钉表格支持行级权限，也可以做单表 + 角色规则；但**没有验证过钉钉表格的行级权限能做到“本人只看自己、HRD看全部”时，优先用“个人表 + 汇总表”**，不要拿一张共享表赌权限。

## 个人台账表

- 第一行使用 38 个标准字段，默认视图顺序见 `field-mapping.md`。
- 一人一行；同一候选人投不同岗位分行。
- 不放 `resumeId` 到可见字段里；内部同步报告保留 `resumeId` 用于幂等。
- 新行追加到末尾；已有行只更新变化字段。
- 不删除历史行；离职/归档也只改状态。

## 面试反馈明细表

建议列：

`候选人姓名, HR, 招聘岗位, 面试轮次, 面试时间, 面试官, 面试结果, 评分, 面试评语, 能力项评分, 数据状态`

规则：

- 一场面试一行；同一场多人评价时，面试官用“、”连接，评语按“姓名：内容”拼接。
- 结果写 `通过 / 未通过 / 部分评价 / 未评价 / 邀约待确认`。
- `数据状态` 写 `已评价 / 部分评价 / 未评价 / 待复核`，不要只写结果。
- 面试评语原文保留；不要摘要成“表现不错”这种二次加工文本。

## 公开漏斗表

只放聚合字段，例如：

`HR, 周期, 接收简历, 推荐, 业务复筛通过, 安排面试, 实际面试, 面试通过, offer, 待入职, 入职, points, 排名`

- 不放姓名、手机号、最近公司、面评原文、推荐备注。
- HR 之间可见、可排名；HRD/招聘运营看全量。
- points 权重由 HRD 在 `score_rules` 中确认；未确认时全部为 0。
- 排名可按 points，也可按“推荐→面试→offer”转化率；口径写在表头或口径说明区。

## 钉钉写入策略

1. 用 `dws` CLI 时先执行 `dws aitable --help` / `dws aitable <path> --help`，以实时命令为准；AI 表格记录查询、创建、更新示例见 `aitable-api.md`。
2. 如果 `dws` 没有表格追加/更新命令，用浏览器操作钉钉表格，或把 CSV 导入/粘贴到目标表；不要为了自动化去改表结构。
3. 写入前先读表头和现有业务键；标准字段缺失或视图顺序异常时停止。
4. 写入顺序：个人台账 → 面试反馈 → 公开漏斗；任一步失败，后面的步骤停止并报告。
5. 首次写入必须 `dry_run`，让用户确认 CSV；确认后再开 `dry_run=false`。
6. 不整表覆盖、不清空、不删除用户手工补的行；视图列顺序按标准配置维护。
7. 每次同步在 `sync_report.json` 记录：新增、更新、跳过、异常；不要记录密码/Cookie/token。

## 权限落地检查

- 用另一个 HR 账号（不是 HRD）打开个人台账，确认看不到别人的明细。
- 用普通 HR 账号打开公开漏斗，确认能看到所有人的聚合和排名。
- 用 HRD/招聘运营账号打开个人台账，确认能看到全量。
- 公开漏斗里搜索候选人姓名，确认搜不到。
- 个人台账链接不要发到全员群；只发本人和 HRD/招聘运营。

## 与旧台账的关系

- 旧台账的历史行可以迁移，但不要用旧 HR 姓名直接当新 `jobOwners`；迁入时映射到标准字段。
- 旧台账的 `HR姓名` 可能包含已离岗/非当前高招组人员；迁移时建立“旧姓名 → 当前 ownerId/姓名”映射。
- `02个人漏斗数据` / `03岗位漏斗数据` 里的 `#REF!` 公式不要直接迁移；用新的聚合表重算。
- 旧台账的“简历推荐是否通过”和“HR沟通结果”常重复；新表保留两列，但口径按 `field-mapping.md` 区分“推荐结果”和“复筛结果”。
